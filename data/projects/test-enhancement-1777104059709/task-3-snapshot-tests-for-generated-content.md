# Task 3: Snapshot Tests for Generated Content

## 1. Context

Task 3 pins the outputs of every Python prompt function and the two TypeScript document-generator functions by adding golden-file assertions. On the Python side, `syrupy` writes one `__snapshots__/test_prompts.ambr` file on the first run and diffs against it on every subsequent run; any change to a prompt function produces a visible, reviewable PR diff before reaching production. On the TypeScript side, Karma `toEqual` assertions compare the live output of `generateSpecIndex()` and `generateTimeline()` against committed fixture objects in `src/app/spec/fixtures/generators/`; updates are always explicit, tracked edits to a source file. This task adds zero new production code — it only observes and pins outputs of logic that Task 1's infrastructure baseline already reaches in unit form.

**Trade-offs considered:**
- Jasmine 4+ snapshot API considered — support is unconfirmed in this project's Karma/Jasmine version; `toEqual` + committed fixture objects is the conservative fallback that works across all Jasmine versions without an additional dependency
- Custom `open("golden.txt")` approach considered — rejected because syrupy integrates with pytest's diff output and provides `--snapshot-update` as a single-command regeneration; a hand-rolled comparison produces no pytest diff on failure and requires manual golden-file management
- Storing TypeScript fixtures as JSON files considered — rejected because `.ts` fixture files are importable directly without `JSON.parse`, are type-checked by the compiler, and produce cleaner PR diffs than raw JSON

### Step 4: Write the Python snapshot test file

**Action**: Create `server/modules/ai/tests/test_prompts.py`. One test class per prompt function. Each test calls the function with a small, deterministic, stable input and asserts `result == snapshot`. Mark every test `@pytest.mark.snapshot`.

**File**: `server/modules/ai/tests/test_prompts.py` (new)

**Pattern** (executor adapts imports to match Step 3 discovery):
```python
"""Snapshot tests for prompt functions in modules.ai.prompts.

Run:    pytest -m snapshot
Update: pytest -m snapshot --snapshot-update
"""
import pytest
from modules.ai.prompts.analysis import build_analysis_prompt
from modules.ai.prompts.epic import build_epic_prompt
from modules.ai.prompts.architecture import build_architecture_prompt
from modules.ai.prompts.implementation import build_implementation_prompt
from modules.ai.prompts.rewrite import build_rewrite_prompt

# Minimal, stable inputs — NOT realistic production values.
# Smallest inputs that produce a complete, deterministic golden string.
_BRAINDUMP = "A tool that helps solo founders write better product specs."
_PRODUCT    = "SpecDoc"
_ANALYSIS   = "Problem: founders write vague specs. Constraint: solo developer."
_EPIC       = "Scope: spec generator MVP. Tasks: bootstrap, edit, export."
_ARCH       = "Flask backend, Angular frontend, Claude AI."
_TASK       = "bootstrap-flow"
_TEXT       = "Make this text better."
_INSTRUCTION = "Expand with more detail."


class TestAnalysisPrompt:
    @pytest.mark.snapshot
    def test_minimalBraindump_returnsStablePrompt(self, snapshot):
        assert build_analysis_prompt(_BRAINDUMP) == snapshot

    @pytest.mark.snapshot
    def test_emptyBraindump_returnsStablePrompt(self, snapshot):
        assert build_analysis_prompt("") == snapshot


class TestEpicPrompt:
    @pytest.mark.snapshot
    def test_analysisAndProductName_returnsStablePrompt(self, snapshot):
        assert build_epic_prompt(_ANALYSIS, _PRODUCT) == snapshot


class TestArchitecturePrompt:
    @pytest.mark.snapshot
    def test_epicContent_returnsStablePrompt(self, snapshot):
        assert build_architecture_prompt(_EPIC) == snapshot


class TestImplementationPrompt:
    @pytest.mark.snapshot
    def test_architectureAndTaskName_returnsStablePrompt(self, snapshot):
        assert build_implementation_prompt(_ARCH, _TASK) == snapshot


class TestRewritePrompt:
    @pytest.mark.snapshot
    def test_textAndInstruction_returnsStablePrompt(self, snapshot):
        assert build_rewrite_prompt(_TEXT, _INSTRUCTION) == snapshot

    @pytest.mark.snapshot
    def test_emptyInstruction_returnsStablePrompt(self, snapshot):
        assert build_rewrite_prompt(_TEXT, "") == snapshot
```

# Expect: all tests pass, each line shows "SNAPSHOT WRITTEN"

## 10. Out of Scope

This task adds test files and one dev-requirements entry. Its blast radius is strictly confined to the test layer — no production files change, no new routes, no new prompt logic, no schema migrations. The following was explicitly considered and deferred; the executor MUST stop and flag rather than absorbing any item below.

- **Improving prompt output quality** — if a golden looks wrong or suboptimal after being written, commit it as-is. Prompt changes belong in a separate task focused on prompt engineering, not here.
- **Parametrizing the prompt matrix** — the architecture mentions a parametrized matrix for route shapes; prompt snapshot tests are a distinct concern and do not have enough variation to justify a matrix yet. Trigger: a second calling context for the same prompt function.
- **DOM or component snapshot testing** — snapshotting rendered HTML in Karma is different from `toEqual` against a generator output; Angular template snapshots require a confirmed Karma/Jasmine mechanism and belong in a follow-on task once the E2E layer (Task 5) is proven.
- **`--snapshot-update` in CI** — adding this flag to `make ci` would silently regenerate goldens on every CI run, defeating the purpose of the golden layer. The flag is local-only. Trigger for CI promotion: a prompt-release workflow that needs controlled regeneration per deploy.
- **Coverage thresholds for the snapshot layer** — pure-string template functions produce trivially high line coverage; enforcing a threshold gate here adds no signal. Coverage is surfaced as a CI artefact and reviewed per sprint, not gated per commit.
- **Snapshot tests for any prompt functions not discovered in Step 3's grep** — the executor adds exactly one snapshot test per function the grep returns, nothing more.

**Rule for the executor**: if a change appears helpful but appears in this list, STOP and flag it as a deviation rather than expanding this task's blast radius.
