# 🏗️ Solution Architecture: Thin API Phase 3

## Architecture Overview

Phase 3 reframes the AI surface as a **facade of named verbs**. Today's `/api/ai/text/rewrite` is a generic instruction-pipe: the frontend hands the backend a prompt and a payload, and Flask is just transport. After Phase 3, the API becomes the contract — eight action-named routes, each one a noun in the product's vocabulary (`brainstorm`, `expand`, `compress`, `clarify`, `simplify`, `tldr`, `bullets`, `rewrite`). The HTTP method name *is* the AI behaviour. Instructions live in SKILL.md files; Flask routes are ~10-line dispatchers; Angular is a regenerated client that has never heard the word "prompt".

The mental model is three concentric rings. **Ring 1 (Angular)** knows only that `brainstorm(text)` returns `{ text, latencyMs }` — no prompts, no system messages, no `join('\n')`. **Ring 2 (Flask)** knows the contract from `openapi.yaml` and which skill to invoke per action — no prompt strings. **Ring 3 (SKILL.md + Claude)** owns every instruction. A prompt tweak is a file save in Ring 3; nothing in Rings 1 or 2 needs to move. This collapses the prompt-iteration loop from "edit TS → rebuild Angular → deploy → invalidate cache" to "edit SKILL.md → reload skill".

The key insight is that **the existing chain adapter already gives us this boundary** — we just stopped at the wrong level of abstraction in Phase 1 by exposing `rewrite(text, instruction)` to the client. Phase 3 finishes the job by hiding `instruction` behind action names. The bootstrap async pattern (202 + job_id + polling) is reused unchanged for any future long-running action; Phase 3 itself only deals with synchronous text actions, so no new background-job machinery is introduced.

## Design Principles

| Principle | Application |
|-----------|-------------|
| **P1 — Adapter Boundary** | Every route calls the skill layer, which calls `modules/runtime/chain/adapter.py`. No route handler imports a provider. The adapter remains the single AI call boundary. |
| **P2 — Thin HTTP Layer** | Each of the eight Flask handlers is validate → invoke skill → return. No prompt assembly, no instruction strings, no branching beyond required-field checks. The 15-line ceiling is the architectural enforcement mechanism. |
| **P4 — No Speculative Abstractions** | Eight near-identical 10-line route handlers beat one parametrised dispatcher. A registry of `{action: skill_name}` would save ~60 LOC and obscure the contract; we keep them flat and named. |
| **P5 — OpenAPI-First** | `openapi.yaml` defines the eight routes and the locked `{ text, latencyMs }` response. Angular's client is generated by `ng-openapi-gen` — never hand-edited. Routes implement the contract; the contract does not implement the routes. |
| **P6 — Skills First** | The six new actions ship as SKILL.md files, not as Python prompt builders. Skills reference shared style/voice from existing context files rather than re-stating them inline. |
| **P7 — File Size & Structure** | The new `routes/text.py` blueprint stays under 200 LOC even with eight handlers because each is trivial. `ai.service.ts` shrinks from instruction-heavy to a thin facade well under 200 LOC. |
| **Facade over passthrough** | The API exposes verbs the product cares about, not generic AI primitives. "Concise" is a contract value the backend interprets; the client never learns what it means to Claude. |

## Component Design

### `/api/text` Blueprint (Flask)

**Purpose**: Translate eight action-named HTTP requests into skill invocations and return the locked response shape.

The blueprint owns one file (`api/modules/ai/routes/text.py`) with eight handler functions — `brainstorm`, `expand`, `compress`, `clarify`, `simplify`, `tldr`, `bullets`, `rewrite`. Each handler authenticates, pulls `text` (and `style` for rewrite, optional `question`/`context` for brainstorm) from the JSON body, calls the corresponding skill via the chain adapter, measures latency, and returns the response. There is no shared base function and no dispatch table — the duplication is intentional and within the noise threshold P4 endorses. Handlers do not concatenate prompts, do not pick model parameters, and do not interpret skill output.

The brainstorm handler is the only one with optional fields. When `question` is present, the body shape signals followup mode; the SKILL.md branches on payload shape so the route stays the same. This collapses what was nearly a separate `/brainstorm-followup` route into a single endpoint.

### SKILL.md Library (Plugin)

**Purpose**: House every AI instruction as an editable, reloadable, version-controlled markdown file.

`brainstorm` and `rewrite` SKILL.md files exist already from Phase 2. Phase 3 adds six siblings — `expand`, `compress`, `clarify`, `simplify`, `tldr`, `bullets` — written in the same template. The `rewrite` skill receives the `style` parameter and maps the five vocabulary values (Concise, Technical, Executive, Narrative, Punchy) to instruction shapes inside the skill, never in Python. Skills reference the existing voice/tone references rather than restating them — preserving the "references are the single source of truth" principle.

The six new skills are sibling files of identical structure, not subclasses of a meta-skill. If a seventh skill needs unusual behaviour, that's a fresh SKILL.md, not a registry entry.

### `openapi.yaml` Contract

**Purpose**: Single source of truth for route paths, request schemas, and the locked `{ text, latencyMs }` response.

The contract names eight paths under `/api/<action>`, each with a request body and the shared `TextResponse` schema. `brainstorm` declares optional `question`/`context`; `rewrite` declares required `style` with the five allowed values as an enum. `latencyMs` is mandatory and integer-typed — clients can show "took 1.2s" without inferring it. The contract is consumed by both the Flask test suite (request/response shape assertions) and `ng-openapi-gen` (generates the Angular client).

Adding a ninth action is a three-file diff: append to `openapi.yaml`, drop a SKILL.md, add a 10-line route. The success-criteria walkthrough is satisfied because no file mutates outside of additions.

### Angular Generated Client + AiService Facade

**Purpose**: Provide typed methods on the frontend with zero awareness of AI behaviour.

`ng-openapi-gen` runs as a build step against `openapi.yaml` and emits typed services and DTOs into a generated folder. `ai.service.ts` becomes a hand-written facade *over* the generated client — exposing the eight methods the UI components already call (`brainstorm`, `expand`, etc.), each delegating to the generated client in 2–3 lines. We keep the facade because the Angular components import `AiService`; replacing component imports site-wide is bigger churn than wrapping. The facade has no instruction strings, no `join('\n')`, no system-prompt concepts.

`app.component.ts`'s `followupBrainstorm()` method currently assembles a context-laden instruction string. After Phase 3 it becomes one line: `aiService.brainstorm(text, { question, context })`. The skill — not the Angular code — decides how to use those optional fields.

### Dead Code Removal Boundary

**Purpose**: Define exactly what disappears so cleanup is mechanical, not judgmental.

Phase 3 deletes `text_prompts.py` (423 LOC) and the five orphan routes (`/rewrite`, `/generate`, `/iterate`, `/lint-braindump`, `/review`) plus their tests. It does **not** delete `task_gen.py`, `quality/`, `bootstrap-project`, or `generate-epic-guide` — those remain Python-backed because their async pipelines are out of scope (deferred to Phase 4 per the epic). The deletion boundary is the seam between "synchronous text action" (gone, migrated to skill) and "multi-step async chain" (still Python, still uses the existing 202 + polling pattern).

## Technology Stack

| Layer | Choice | Rationale |
|-------|--------|-----------|
| HTTP contract | OpenAPI 3.1 in `openapi.yaml` | Single source of truth; client generation eliminates hand-written HTTP code; matches P5 across the rest of spec-doc. |
| Backend routes | Flask Blueprint (`routes/text.py`) | Existing pattern; thin handler ceiling enforced by P2 and P7; no new framework introduced. |
| AI dispatch | Existing chain adapter → SKILL.md via `claude --agent chain-agent` | Already the only AI call boundary; no new abstraction; skills reload without restart. |
| Skills format | SKILL.md per action | P6 default; iterates without rebuild; references rather than duplicates voice/tone rules. |
| Frontend client | `ng-openapi-gen` from `openapi.yaml` | Removes hand-written HTTP and DTOs; regenerates on contract change; types flow into components automatically. |
| Frontend facade | `AiService` over generated client | Preserves component-side import surface; isolates the generated code so consumers never touch it directly. |
| Background jobs | None new | Phase 3 is synchronous-only; the existing 202 + in-process dict pattern stays untouched for bootstrap/epic-guide. |

## Design Decisions

| Decision | Rationale | Trade-offs |
|----------|-----------|------------|
| Eight flat routes (`/api/brainstorm`) instead of one parametrised route (`/api/text/<action>`) | The verb is the contract. Flat routes show up in OpenAPI as named operations, generate named TS methods, and read like product behaviour in the codebase. A parametrised route would push action-name validation into runtime and obscure the surface. | More repetition in `text.py`; eight rather than one OpenAPI entry. Accepted under P4 — three similar lines beat a premature dispatcher. |
| Eight near-identical handlers, no shared base function | P4 explicitly endorses three similar lines over abstraction. A `_run_skill(action, body)` helper would save ~50 LOC but couple all eight routes to one signature; brainstorm's optional fields and rewrite's required `style` already break the symmetry. | LOC duplication; eight test cases instead of one parametrised test. Worth it for handler clarity and the 15-line success criterion. |
| Hand-written `AiService` facade *over* the generated client (not replacing it directly) | Angular components import `AiService` widely; rewriting every consumer to take the generated client is out of scope and risks regression in untested call sites. The facade is a stable seam. | Two layers instead of one. The facade must be kept in sync with the generated method names — but since both come from the same `openapi.yaml`, drift is mechanical to detect. |
| Brainstorm followup folded into `/api/brainstorm` via optional fields, not a separate `/brainstorm-followup` route | Same skill, same response, same auth — only the payload shape differs. A second route would duplicate the contract and force the frontend to choose; the skill is better placed to branch on payload presence. | The skill takes on a tiny dispatch responsibility. Acceptable because it's localised in one SKILL.md, not spread across Python and TS. |
| `rewrite` keeps a `style` parameter with five enum values, rather than five separate routes | "Concise" / "Technical" / "Executive" / "Narrative" / "Punchy" are variations on one action, not different actions. Five routes would balloon the surface and force the UI to track which is which. The enum lives in OpenAPI so clients still get typed values. | The `rewrite` route is asymmetric with the other seven (extra required field). Accepted as a deliberate exception — style is product vocabulary, not implementation detail. |
| Drop `/api/ai/text/generate` with no replacement | It is not a clear product action; it was a generic AI primitive. Keeping it would re-introduce the passthrough we're removing. | One existing capability disappears. Acceptable per epic scope — no caller depends on it. |
| Defer `bootstrap-project` and `generate-epic-guide` skill migration to Phase 4 | They're multi-step async chains with non-trivial state machines. Migrating them in Phase 3 widens the blast radius and risks the synchronous-text cleanup. Async migration deserves its own design pass. | `task_gen.py`, `workflows/spec_gen/`, and parts of `text_prompts.py` survive Phase 3 even though they look like cruft. The deletion list is smaller than the braindump suggested — the architecture document is the definitive boundary. |
| No new background-job infrastructure in Phase 3 | All eight new actions are synchronous and well under the 30s threshold from P3. Adding 202 + polling for them would violate P4. | If a future text action turns out to be slow (e.g. very long input), it would need to migrate to async. Mitigated by the chain adapter already supporting both modes. |
| Drop the `/text/` and `/ai/` URL prefixes | The product treats these as first-class verbs, not as a sub-resource of an "AI" namespace. Flat URLs match the product mental model and shorten the OpenAPI document. | Old URLs return 404 immediately rather than redirecting. Acceptable — no external clients exist; the only consumer is the spec-doc Angular app, which regenerates against the new contract in the same commit. |
| Locked response shape `{ text, latencyMs }` | All eight actions return one piece of generated text; `latencyMs` is observable telemetry the UI already shows. Locking it in OpenAPI prevents per-action drift and lets the generated client share a single DTO. | Future actions that want to return structured data (e.g. multiple variants) must extend the schema additively — they cannot replace the field. Worth it for client simplicity. |
