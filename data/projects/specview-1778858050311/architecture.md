# 🏗️ Solution Architecture: SpecView — Launch-Ready Product Definition

## Architecture Overview

SpecView's launch challenge is not an engineering problem — it is an explanation problem. The system already generates specs from brain dumps, already handles auth and project CRUD, and already serves a static landing page. What is missing is the connective tissue between a stranger arriving cold at a URL and that stranger becoming a user who understands the product through experiencing it. The architecture for this epic therefore designs three surfaces — explanation, demonstration, and onboarding — and defines how they compose from existing infrastructure without introducing new services or endpoints.

The key architectural insight is that SpecView's best explanation **is its own output**. Rather than writing marketing copy that describes spec generation in the abstract, the explanation surface should showcase SpecView's own spec set — the very documents generated by the product about itself. This dogfood-as-demo strategy eliminates the credibility gap that plagues most dev-tool launches: the product's quality is immediately verifiable because the visitor is reading a live artifact, not a promise. The architecture routes a cold visitor through three phases: a static landing surface that establishes the one-liner and value prop, a read-only showcase of SpecView's own generated specs as proof of output quality, and a guided entry into the authenticated app where they paste their first brain dump.

The existing codebase already contains every component needed. The `landing/` static site handles the cold-visit surface. The Angular SPA at `web-ng/` handles the authenticated experience. The Flask API serves project data. No new services, no new endpoints, no new infrastructure. The architecture work is composition and flow design — wiring existing pieces into a coherent first-visit journey.

## Design Principles

| Principle | Application in This Epic |
|-----------|--------------------------|
| P4 — No Speculative Abstractions | No CMS, no templating engine, no dynamic landing page framework. The landing page is static HTML served by nginx. Copy changes are file edits, not database updates. |
| P2 — Thin HTTP Layer | If any API surface is needed for the showcase view, it reuses existing project-read endpoints. No new route handlers for launch content. |
| P7 — File Size & Structure | The landing page remains a single focused HTML file with inline styles. No build toolchain for a page that changes once per launch. |
| P6 — Channel-Aware Output | Launch distribution copy must work across channels — Twitter/X character limits, Product Hunt structured fields, direct URL shares with OG metadata. Each channel gets purpose-fit copy, not one-size-fits-all. |
| Dogfood as Architecture | SpecView's own project spec set is a first-class architectural component, not a side artifact. It must pass coherence linting because it serves as both demo content and product validation. |

## Component Design

### Explanation Surface (Landing Page)

**Purpose**: Convert a cold visitor into a curious one within 30 seconds.

The existing `landing/` directory already serves a static page via nginx:alpine. This surface gains three elements: the product one-liner (derived from Task 1's positioning work), a visual walkthrough showing the brain-dump-to-spec-set transformation, and a single call-to-action that routes to either the showcase or the signup flow. The landing page remains fully static — no JavaScript framework, no API calls, no dynamic content. This is deliberate: the explanation surface must load instantly, work without authentication, and survive any API downtime. A stranger's first impression cannot depend on a background thread completing.

The trade-off is that updating the landing page requires a file edit and redeploy rather than a CMS update. For a solo developer launching once, this is the correct trade-off. A CMS would be speculative infrastructure for a problem that does not yet exist (frequent copy iteration by non-technical users).

### Dogfood Showcase (Read-Only Spec View)

**Purpose**: Prove output quality by showing SpecView's own generated specs before the visitor commits to signing up.

The showcase presents SpecView's own project — analysis, epic, architecture, timeline — as a navigable read-only artifact. The critical design question is where this lives: inside the authenticated Angular app (requiring signup first) or as a public route accessible without auth.

The architecture places the showcase **outside the auth boundary** as a pre-authenticated experience. A visitor who must sign up before seeing what the product produces will bounce. The showcase is the bridge between "I understand what this claims to do" and "I believe it actually does it." Placing the bridge behind a gate defeats its purpose.

Implementation-wise, this can be achieved through the existing Angular app with a public route that reads a designated showcase project, or through pre-rendered static content embedded in the landing surface. The static approach is preferred for launch: it eliminates the dependency on the API being available during the visitor's first impression, and it avoids building a public-access API path that would need security review. The showcase content is generated once by SpecView, exported, and embedded. It updates only when the dogfood specs are regenerated.

The trade-off: static showcase content can drift from the actual generated output if specs are updated without re-exporting. This is acceptable for launch and becomes a problem only if the dogfood specs change frequently post-launch.

### Onboarding Flow (Authenticated App)

**Purpose**: Take a convinced visitor from signup through their first generated spec set with zero dead ends.

The onboarding flow is not a separate component — it is a **state-aware path through the existing Angular SPA**. When a user has zero projects, the app's default view should not be an empty dashboard with a "Create Project" button buried in a menu. It should be a focused prompt: name your project, paste your brain dump, watch specs generate. The empty-state design is the onboarding design.

This approach avoids building a parallel onboarding system (tutorial overlays, step wizards, onboarding-specific routes) that would need maintenance alongside the main app. The main app simply behaves differently when there is nothing to show yet. The trade-off is that future power-user features on the dashboard (project search, filters, bulk actions) must coexist with the empty-state onboarding — but those features do not exist yet, and P4 says not to design for them until they do.

### Coherence Validation Layer (Dogfood Quality Gate)

**Purpose**: Ensure SpecView's own spec set is credible enough to serve as the product demo.

The existing `quality/` module already provides `lint_task_guide()` as a pre-write quality gate. For launch, this linting must also validate the dogfood project's full spec set: cross-references resolve, no content-routing violations (status words outside timeline, code blocks outside implementation guides), and the spec set reads as a coherent narrative rather than disconnected documents.

This is not a new linting system — it is running the existing linter against a specific project and treating failures as launch blockers. The architectural decision is that the dogfood project is held to the same quality standard as any user's project. No special cases, no manual overrides. If the linter cannot pass SpecView's own specs, either the specs or the linter needs fixing — both outcomes improve the product.

### Launch Distribution Layer (Copy and Channels)

**Purpose**: Prepare channel-specific launch messages that drive traffic to the explanation surface.

This is a content architecture problem, not a software architecture problem. The distribution layer produces static artifacts — tweet text, Product Hunt listing copy, direct-share message — that link to the landing page URL. No scheduling system, no automated posting, no analytics pipeline. Sam posts manually on launch day.

The architectural constraint is OG metadata: when the URL is shared, the link preview must show the product one-liner and a representative image. This requires `<meta>` tags in the landing page's `<head>`, which is already achievable in the static nginx setup. No server-side rendering needed.

## Technology Stack

| Layer | Choice | Rationale |
|-------|--------|-----------|
| Explanation Surface | Static HTML via `landing/` (nginx:alpine) | Zero dependencies, instant load, survives API downtime. No framework overhead for a page that changes rarely. |
| Showcase Content | Pre-rendered spec output embedded in landing or served as static assets | Eliminates auth dependency for first impression. No public API paths to secure. |
| Onboarding Flow | Existing Angular SPA (`web-ng/`) with empty-state design | Reuses authenticated app — no parallel onboarding system to maintain. |
| Quality Gate | Existing `quality/` module linter | Already built, already validates spec structure. Apply to dogfood project as launch gate. |
| Distribution | Static copy artifacts + OG meta tags | Manual posting is correct for a solo launch. Automation is speculative at this scale. |
| Hosting | Existing Docker Compose → Coolify pipeline | No new services. Landing, API, and SPA already deployed. Launch is a content update, not an infra change. |

## Design Decisions

| Decision | Rationale | Trade-offs |
|----------|-----------|------------|
| Showcase outside auth boundary | A visitor who must sign up before seeing output quality will bounce. The product's best pitch is a live artifact, not a description. | Static showcase can drift from live output. Acceptable for launch; re-export on spec changes. |
| Static landing over dynamic framework | Launch is one event. The landing page changes once (now) and may change again after launch metrics arrive. A framework solves a frequency-of-change problem that does not exist yet. | Updating copy requires file edit + deploy. Fine for solo developer. |
| Empty-state as onboarding | Building a separate onboarding wizard creates a parallel system that must stay in sync with the main app. Making the app's zero-project state be the onboarding path means one system to maintain. | Future dashboard features must coexist with the empty-state path. Design that bridge when those features exist (P4). |
| Dogfood project held to standard linting | If the linter cannot pass the product's own specs, the linter or the specs need improvement. Both outcomes benefit users. Special-casing the demo project would undermine credibility. | Linter bugs become launch blockers. This is a feature, not a risk — it forces quality. |
| No analytics for launch | Adding Plausible, Mixpanel, or even simple event tracking is real work with real privacy implications. Launch success is measurable through simpler signals: signups, projects created, specs generated — all visible in the existing data layer. | No funnel visibility (where do visitors drop off?). Add tracking after launch if drop-off diagnosis is needed. |
| Manual distribution over scheduled posting | Automated launch posting (Buffer, scheduled tweets) adds tooling for a one-time event. Sam posts manually, responds to comments in real time, adjusts messaging based on immediate feedback. | No automation safety net if Sam is unavailable at launch time. Acceptable risk for a solo launch with flexible timing. |
| OG metadata in static HTML over dynamic SSR | Link previews need a title, description, and image. These are static `<meta>` tags — no server-side rendering framework needed for three lines of HTML. | Preview content cannot vary per shared URL path. Every share shows the same card. Fine for a single-product launch. |

## Integration Points

The launch architecture touches existing systems at three points, none of which require modification to the systems themselves:

**Landing → Angular SPA**: The landing page's call-to-action links to the Angular app's signup or login route. This is a standard href — no API integration, no state passing. The visitor's mental context carries over through the explanation they just read, not through a technical handoff.

**Angular SPA → Flask API**: The onboarding flow uses existing project-creation and spec-generation endpoints. The empty-state UI triggers the same API calls that the normal project flow does. No onboarding-specific endpoints.

**Linter → Dogfood Project**: The coherence validation runs against the project stored at `data/projects/<specview-project-id>/`. This is the same path and format as any user project. The linter does not know it is validating the product's own demo.

## Risk Boundaries

**Content risk outweighs technical risk.** The architecture introduces no new services, no new endpoints, no new infrastructure. The risk is that the positioning copy does not resonate, the showcase specs are not compelling, or the onboarding flow has UX friction that testing did not catch. These are content and design risks, not system risks. The mitigation is iteration speed: static content can be updated and redeployed in minutes, not hours.

**The dogfood quality gate is the highest-leverage risk mitigation.** If SpecView's own specs read poorly, no amount of landing-page polish will convert visitors. The architecture deliberately makes spec quality a blocking dependency for launch — not because it is technically necessary, but because it forces the right priority: the product's output quality is the product's pitch.
