## What Worked

**Plugin-direct spec generation is real.** The entire spec set (analysis, epic, architecture, timeline, implementation guide) was produced without the API. The chain-agent read the braindump, used the reference files, and produced accurate, code-aware documents — including exact line numbers in the source files.

**`/exec-guide` executed 5 tasks without human code intervention.** The specialist agents (spec-backend, chain-developer) read the implementation guide, made the file changes, ran pytest, and verified results. The 998 Python lines removed were not touched by a human hand.

**`/dev-review` earned its place.** It caught a real security gap (`bootstrap_cancel`/`bootstrap_retry` missing `@require_auth`) that would have shipped. It also caught the architectural violation (prompt functions inlined into a route file) introduced by the cleanup agent.

**The ratio validates the thesis.** −998 Python lines, +2,077 Markdown lines. The AI logic that lived in Python now lives in skills and agent definitions that any future capability can extend without a deploy.

## What to Improve Next Time

### 1. Validate context files before running the pipeline

`codebase.md` and `versions.md` were stale — describing an old project path and the OpenClaw environment. This affected agent quality for the entire session. The pipeline should include a pre-flight step that checks context file freshness (last modified date, key path presence).

**Fix:** Add a context-check step to `/spec-pipeline` and `/exec-guide`: read `codebase.md`, verify the paths in it match the current `SPEC_DOC_DIR` and project structure. If stale, halt and prompt.

### 2. `/exec-guide` should run `/dev-review` after each task, not just at the end

Task 5 (cleanup) inlined prompt functions into a route file — a convention violation. It was caught by the post-execution review, but required a second fix commit. If `/dev-review` had run after Task 5, the fix would have been part of the same commit.

**Fix:** Add an optional `--review` flag to `/exec-guide`. When set, spawn a `dev-review` agent after each task and block on the result before proceeding to the next.

### 3. `spec-pipeline` skill should offer a plugin-direct path

The `/spec-pipeline` skill still hits `POST /api/ai/text/bootstrap-project`. We proved the plugin-direct path works (we used it for this project), but the skill doesn't encode it. When the API is unavailable or the `prompts/` migration is complete, there's no documented plugin-only fallback in the skill itself.

**Fix:** Add a `## Plugin-Direct Procedure` section to `spec-pipeline/SKILL.md` — already partially done in Task 5, but should be the primary path, not a footnote.

### 4. SPEC_DOC_DIR discovery should be automatic

The skill hardcodes `data/projects/` as the project search path. This broke when `SPEC_DOC_DIR` pointed to `data/spec-doc/` (the Docker convention). The skill had to be manually corrected.

**Fix:** Skills should derive the project path by reading `api/.env` for `SPEC_DOC_DIR` and appending `/projects/`, rather than hardcoding the path. One line of bash: `source api/.env && echo $SPEC_DOC_DIR/projects`.

### 5. impl-guide epic parsing assumes a task table

The epic for this project didn't have a traditional `### Task N:` table — tasks were implicit in the architecture and timeline. The `impl-guide` skill handled it by treating phases as tasks, but this was an inference, not a spec. If the epic format changes, the skill breaks silently.

**Fix:** The `impl-guide` skill should explicitly state the expected epic format and fall back gracefully when tasks can't be parsed — outputting a single narrative guide rather than silently hallucinating task numbers.

### 6. Reflection should be automatic, not manual

This document was written manually after the push. It should be generated by the pipeline automatically — a structured look-back on what was planned vs executed, git stats, review findings, and lessons.

**Fix:** Add `/reflect <project>` as the final step in the pipeline, producing `reflection.md` in the project directory. This is implemented below.

### 7. Docker and local dev SPEC_DOC_DIR are misaligned

Projects written locally at `data/projects/` are not visible in the Docker container (which uses `/data/spec-doc/projects/`). The two environments write to different paths and the files don't cross over.

**Fix:** Add a volume mount in `docker-compose.override.yml`: `- ./data:/data/spec-doc` to make the local `data/` directory the Docker container's `SPEC_DOC_DIR`. One line fixes the gap permanently.
