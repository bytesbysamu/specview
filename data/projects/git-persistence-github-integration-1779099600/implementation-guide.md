# Implementation Guide: Git Persistence — GitHub Integration

## Overview
This epic adds durable GitHub-backed persistence to Specview so that every spec file generated by the AI pipeline is asynchronously pushed to a user-owned private GitHub repository. The work sequences as follows: Task 1 (GitHub Auth) and Task 2 (DB Schema Migration) run in parallel to establish credentials and storage columns; Task 3 (Repo Provisioning) builds on both to create or adopt the user's repo and backfill existing projects; Task 4 (Async Push-on-Write) wires up the background push worker that fires after every local commit; and Task 5 (Sync Status Indicator) adds the frontend badge so users can see whether each project is synced, pushing, or failed.

## Shared Pre-flight
- Register a GitHub App on GitHub with permissions `contents:write` and `metadata:read`; note the App ID and generate a private key PEM file
- Add environment variables for `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY` (or a mounted secret path), and the GitHub App's callback URL
- Install PyJWT as a dependency for GitHub App JWT generation (httpx is already present)
- Verify the existing `modules/data/git_store.py` module boundary — confirm no feature module imports pygit2 directly
- Confirm the single-worker gunicorn configuration (`--workers 1`) is active, since the in-process push queue requires it
- Ensure Alembic is configured and can connect to the Neon Postgres instance for schema migrations
- Review the existing `openapi.yaml` to understand current endpoint conventions before adding new routes
- Confirm `status-bar.component.ts` exists in the Angular frontend and review its current structure

## Task 1: GitHub Auth + Token Exchange  [Effort: 3 days]

### What
Build the OAuth-style flow that lets a user connect their GitHub account from Specview settings. This creates the credential pipeline — storing the GitHub App installation ID on the User model and producing short-lived installation access tokens on demand for all downstream GitHub API calls.

### Files
- **Create**: `modules/github/__init__.py` — package init for the new github module
- **Create**: `modules/github/auth_service.py` — JWT generation using the GitHub App private key, installation token exchange, `connect(user_id, installation_id)` and `get_token(user_id)` operations, disconnect logic
- **Create**: `modules/github/routes.py` — thin HTTP handlers for the installation callback, disconnect endpoint, and connect redirect
- **Modify**: `openapi.yaml` — add endpoint definitions for `GET /github/callback`, `DELETE /github/connection`, and the connect redirect
- **Modify**: the Angular settings page template and component — add a "Connect GitHub" button that redirects to the GitHub App installation URL, and a "Disconnect" button for connected users
- **Modify**: the Angular settings service or equivalent HTTP service — add methods to call the disconnect endpoint
- **Modify**: environment/config module — add config entries for `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, and the callback URL

### Steps
1. Define the three new endpoints in `openapi.yaml` following existing conventions: the callback route accepts an `installation_id` query parameter and returns a redirect, the disconnect route is a DELETE that clears GitHub credentials, and the connect route redirects the browser to the GitHub App installation page.
2. Create the `modules/github/` package with an `__init__.py` file.
3. Implement `auth_service.py` with two public functions. The `connect` function accepts a user ID and installation ID, validates the installation ID by attempting a token exchange with GitHub, stores the installation ID and `github_connected_at` timestamp on the User row, and returns success or failure. The `get_token` function reads the user's stored `github_installation_id`, generates a JWT signed with the App's private key using PyJWT, exchanges it with GitHub's API for a short-lived installation access token, and returns the token. If the user has no installation ID, it returns None.
4. Implement the route handlers in `routes.py` as thin delegates. The callback handler extracts `installation_id` from the query string, calls `auth_service.connect`, and redirects to the settings page. The disconnect handler calls a service function that nullifies `github_installation_id`, `github_repo_full_name`, and `github_connected_at` on the User model. Validate that the installation ID is a real GitHub installation before persisting it.
5. Load the GitHub App private key from the environment config at service initialization — never from a committed file or the database. Ensure the key is available only within `auth_service.py`.
6. Update the Angular settings page to show a "Connect GitHub" button when the user has no GitHub connection, and a "Disconnect GitHub" button with the connected timestamp when they do. The connect button opens the GitHub App installation URL in the current window. The disconnect button calls `DELETE /github/connection` and refreshes the settings state.
7. Handle the edge case where a user revokes the GitHub App installation externally: when `get_token` receives a 403 or 404 from GitHub during token exchange, clear the stored installation ID and surface the disconnected state.

### Verify
- Clicking "Connect GitHub" in settings redirects to the GitHub App installation page, and completing installation redirects back to Specview with the user's `github_installation_id` populated in the database
- Calling `get_token` for a connected user returns a valid short-lived token that can authenticate against the GitHub API
- Clicking "Disconnect GitHub" clears all GitHub columns on the User model and subsequent calls to `get_token` return None
- The callback endpoint rejects an invalid or fabricated `installation_id` without storing it

## Task 2: DB Schema Migration  [Effort: 1 day]

### What
Add the database columns needed for GitHub connection tracking on the User table and sync state tracking on the Project table. These are all additive nullable columns that require no backfill and no downtime.

### Files
- **Create**: a new Alembic migration revision file under the migrations/versions directory — adds six columns across two tables
- **Modify**: the User SQLAlchemy model — add `github_installation_id` (BigInteger, nullable), `github_repo_full_name` (String, nullable), and `github_connected_at` (DateTime, nullable)
- **Modify**: the Project SQLAlchemy model — add `remote_push_sha` (String(40), nullable), `sync_status` (String(20), server default "pending"), `last_push_at` (DateTime, nullable), and `last_push_error` (Text, nullable)
- **Modify**: the project serializer or schema — include the four new Project fields in API responses

### Steps
1. Generate a new Alembic revision using the autogenerate command or by creating a manual revision file.
2. In the upgrade function, add three columns to the User table: `github_installation_id` as a nullable BigInteger, `github_repo_full_name` as a nullable VARCHAR, and `github_connected_at` as a nullable TIMESTAMP. Then add four columns to the Project table: `remote_push_sha` as a nullable VARCHAR(40), `sync_status` as a VARCHAR(20) with a server default of "pending", `last_push_at` as a nullable TIMESTAMP, and `last_push_error` as nullable TEXT.
3. In the downgrade function, drop all seven columns in reverse order.
4. Update the User SQLAlchemy model class to declare the three new columns with matching types and nullability.
5. Update the Project SQLAlchemy model class to declare the four new columns with matching types, ensuring `sync_status` has a default value of "pending".
6. Update the project serializer or Pydantic schema so that API responses for project details include `sync_status`, `remote_push_sha`, `last_push_at`, and `last_push_error`.

### Verify
- Running `alembic upgrade head` completes without errors and the seven new columns are visible in the database schema
- Running `alembic downgrade -1` cleanly removes all seven columns
- Existing User and Project rows are unaffected — all new columns are null (or "pending" for `sync_status`)
- The project detail API response now includes the four new sync-related fields

## Task 3: Repo Provisioning  [Effort: 2 days]

### What
When a user connects GitHub, create (or adopt) a private `specview-projects` repository on their account, write a metadata marker file, and backfill all existing projects into the repo. This ensures every connected user has exactly one repo in a known state with all their current specs already pushed.

### Files
- **Create**: `modules/github/adapter.py` — GitHub REST API wrapper with `create_repo`, `repo_exists`, `push_file`, and `get_file` operations using httpx and the Contents API
- **Create**: `modules/github/provisioning.py` — repo creation/adoption logic, `.specview/config.json` generation, backfill orchestration for existing projects
- **Modify**: `modules/github/auth_service.py` — call provisioning logic after a successful `connect` operation
- **Modify**: `modules/github/routes.py` — ensure the callback handler triggers provisioning after auth completes

### Steps
1. Implement `adapter.py` with four public functions. The `repo_exists` function calls `GET /repos/{owner}/{repo}` and returns a boolean. The `create_repo` function calls `POST /user/repos` to create a private repository with the given name. The `push_file` function calls `PUT /repos/{owner}/{repo}/contents/{path}` with base64-encoded content, a commit message, and optionally the current blob SHA for updates. The `get_file` function calls `GET /repos/{owner}/{repo}/contents/{path}` and returns the file content and SHA. Every function accepts a pre-resolved token as its first argument and raises typed exceptions for HTTP errors.
2. Implement `provisioning.py` with a main `provision_repo(user_id)` function. This function calls `get_token` from the auth service, checks whether a repo named `specview-projects` exists using the adapter, creates it if not, and stores the repo's full name on the User model as `github_repo_full_name`.
3. After repo provisioning, push a `.specview/config.json` file to the repo root containing the user identifier and the connection timestamp. This serves as a format marker for future restore logic.
4. Add a backfill step at the end of provisioning: query all projects belonging to the user, and for each project, read its current files from the local git store and enqueue them for push. Since the push worker from Task 4 may not exist yet, implement a direct synchronous push path in provisioning that uses the adapter to push each file. This path is used only during initial backfill.
5. Wire provisioning into the auth callback flow: after `auth_service.connect` succeeds, call `provisioning.provision_repo`. If provisioning fails, log the error but do not roll back the GitHub connection — the user is connected, and provisioning can be retried.
6. Handle the SHA-based conflict detection in the adapter's `push_file` function: if GitHub returns a 409 (SHA mismatch because someone edited the file on GitHub), fetch the current SHA via `get_file`, and retry the push with the updated SHA. Log a warning that an external edit was overwritten.

### Verify
- Connecting a new user creates a private `specview-projects` repo on their GitHub account with a `.specview/config.json` file at the root
- Connecting a user who already has a `specview-projects` repo adopts the existing repo without creating a duplicate
- After connecting, all existing projects for the user appear as directories in the GitHub repo with their spec files present
- The User model's `github_repo_full_name` field is populated with the correct value after provisioning

## Task 4: Async Push-on-Write  [Effort: 3 days]

### What
Wire up a background daemon thread that pushes every local file commit to GitHub asynchronously, so that the user-facing write path incurs zero additional latency. This is the core durability mechanism — every call to `git_store.write_file` results in a corresponding file appearing in the user's GitHub repo within seconds.

### Files
- **Create**: `modules/github/push_worker.py` — daemon thread, in-process deque with threading lock, retry logic with exponential backoff, sync state updates, consistency sweep, `enqueue` and `start_worker` functions
- **Modify**: the service layer that calls `git_store.write_file` (e.g., `project_service.py` or the equivalent orchestration module) — add an `enqueue` call after each successful local commit
- **Modify**: `modules/github/adapter.py` — add 401 detection and token refresh retry logic
- **Modify**: the application startup module (e.g., `app.py` or the gunicorn entrypoint) — call `start_worker()` on server boot
- **Modify**: `modules/github/routes.py` — add a `POST /projects/{id}/sync/retry` endpoint that re-enqueues a failed project's latest commit
- **Modify**: `openapi.yaml` — add the retry endpoint definition

### Steps
1. Implement `push_worker.py` with an in-process `collections.deque` protected by a `threading.Lock`. The `enqueue` function accepts `user_id`, `project_id`, `filename`, `content`, and `commit_sha`, and appends a job dict to the deque. If the user has no `github_installation_id`, the function returns immediately as a no-op.
2. Implement the `start_worker` function that spawns a `threading.Thread` with `daemon=True`. The thread runs an infinite loop: pop a job from the deque (blocking with a short sleep if empty), set `sync_status = 'pushing'` on the project row, call `auth_service.get_token` to get a fresh token, then call `adapter.push_file` to push the file to GitHub.
3. On a successful push, update the Project row: set `remote_push_sha` to the commit SHA, `sync_status` to "synced", `last_push_at` to the current timestamp, and clear `last_push_error`.
4. On failure, implement exponential backoff retry: wait 1 second after the first failure, 4 seconds after the second, 16 seconds after the third. If all three retries fail, set `sync_status = 'failed'` and write the error message to `last_push_error`.
5. Add 401-handling in the adapter: if a push call returns 401, request a fresh token from the auth service and retry the call once before counting it as a failure.
6. Wire the enqueue call into the existing write path. In the service function that calls `git_store.write_file`, after the local commit succeeds and the database row is updated with `latest_commit_sha`, call `push_worker.enqueue` with the file details and the new SHA.
7. Implement a consistency sweep in the worker thread: every 60 seconds, query all projects where `sync_status` is "pushing" with a `last_push_at` older than 5 minutes (stuck), or where `remote_push_sha` does not equal `latest_commit_sha` (drift). Re-enqueue any such projects for push.
8. Add the retry endpoint in `routes.py`: `POST /projects/{id}/sync/retry` reads the project's latest commit from the database, enqueues a push job for it, and returns 202.
9. Call `start_worker()` during application startup so the daemon thread is running before any requests are served.

### Verify
- Running a full pipeline that generates multiple spec files results in all files appearing in the user's GitHub repo within 30 seconds of pipeline completion
- The `sync_status` column transitions through "pending" to "pushing" to "synced" during a successful push, and `remote_push_sha` matches `latest_commit_sha`
- Temporarily making the GitHub API unreachable causes `sync_status` to move to "failed" after three retries, and `last_push_error` contains a meaningful message
- Calling `POST /projects/{id}/sync/retry` on a failed project re-enqueues the push and eventually moves the status back to "synced"

## Task 5: Sync Status Indicator  [Effort: 1 day]

### What
Add a visual sync badge to the existing status bar component so users can see at a glance whether each project is synced to GitHub, currently pushing, or in a failed state with a retry option. This reads the `sync_status` field already returned by the project API — no new data fetching is required.

### Files
- **Modify**: `status-bar.component.ts` — add sync status badge rendering logic that reads `sync_status` from the project object
- **Modify**: the status bar template (the corresponding `.html` file) — add the badge markup with conditional display for synced (green check), pushing (animated spinner), and failed (red warning with retry button)
- **Modify**: the status bar stylesheet (the corresponding `.css` or `.scss` file) — add styles for the three badge states
- **Modify**: `projects.service.ts` or the equivalent Angular service — add a method to call the `POST /projects/{id}/sync/retry` endpoint when the user clicks the retry action

### Steps
1. In the status bar template, add a sync badge element next to the existing generation status display. Use conditional rendering to show one of three states based on the project's `sync_status` field: a green checkmark icon for "synced", an animated spinner icon for "pushing", and a red warning icon for "failed".
2. For the "failed" state, make the badge clickable and wire it to a retry action. When clicked, call the project service method that posts to `POST /projects/{id}/sync/retry`, then update the local badge state to "pushing" optimistically while the retry processes.
3. Add styles for the three badge states. The synced badge should be subtle and non-distracting. The pushing spinner should indicate activity without being alarming. The failed badge should be visually prominent with a cursor pointer to indicate it is clickable.
4. Ensure the badge only appears when the user has a GitHub connection. If `sync_status` is null or the user has not connected GitHub, hide the badge entirely rather than showing an empty or confusing state.
5. The existing polling mechanism that refreshes project state during generation will automatically pick up sync status changes. Verify that no additional polling logic is needed — the badge updates as the project object refreshes.

### Verify
- A project that has been successfully pushed to GitHub shows a green sync badge in the status bar
- During an active push, the badge displays an animated spinner
- A failed sync shows a red warning badge; clicking it triggers a retry and the badge transitions to the spinning state
- When no GitHub account is connected, the sync badge is hidden entirely
